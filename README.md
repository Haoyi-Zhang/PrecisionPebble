# Preparation-aware weighted pebbling

A self-contained research artifact for **Preparation-Aware Weighted Pebbling for Precision-Changing Operator Trees**. This directory is the root of the standalone `tight-pebbling-bounds-precision` repository. It does not require a manuscript directory, private cache, online account, solver service, model API or network connection.

## What is implemented

The planner jointly chooses representations, operator recipes, spill edges and execution order on a rooted unique-consumer in-tree. It exactly minimizes transferred allocation units, with nonnegative rational abstract work as a lexicographic tie-breaker, **only when every allowed recipe's output allocation is at most each operand's allocation**. The bound is pseudo-polynomial in integer capacity. The explicit configuration search is a separate small-instance oracle. The event checker and cut-mask Bellman checker do not import the optimizer. This is implementation separation, not independent authorship or blind review.

`proofs/core.md` gives the general mathematical arguments, including ancestry pruning, the spill-forest identity, component serialization, the exact recurrence, a tight 23t/25t family and an NP-complete expansive extension. These proofs are not mechanized. The recurrence in expansive mode is only a feasible upper-bound policy. No hardware, deployment, energy, floating-point-accuracy or model-performance claim is supported.

## Requirements and bounded clean reproduction

A Linux/POSIX environment with Python 3.10 or newer and its standard library is required. No package installation is needed. The implementation uses exact Python integers and `fractions.Fraction`. The reproduction runner uses POSIX `resource` limits, pins itself to one available CPU, and imposes a 3 GiB address-space limit. The frozen original envelope is four CPUs / 4 GiB RAM, with no swap; all reported experiments used one worker. Run sequentially, never in parallel.

From this directory, create a fresh output directory by choosing a name that does not already exist:

```sh
for step in 1 2 3 4 5 6; do
  python3 reproduce.py --output results/replay --chunk 64 || exit "$?"
done
python3 tools/check_controls.py --output results/replay-controls.json
python3 tools/check_reference_equation.py --output results/replay-reference-equation.json
python3 -m unittest discover -s tests -v
python3 tools/summarize.py --results results/replay --output results/replay-summary
python3 tools/compare_replay.py --reference results/evaluation --replay results/replay --output results/replay-comparison.json
```

Six invocations process the retained 364 cases. The reference-equation command independently evaluates the fixed-state recurrence printed as Eq. (6) in the anchor paper, plus its Eq. (7) root store, on five declared controls. Each invocation resumes existing checked records rather than silently overwriting them. An existing directory is a continuation, **not** a clean replay. A status ending in `cap`, a nonzero command exit, or fewer than 364 checked records invalidates a completion claim. Do not omit failed cases, increase the frozen caps, or call a missing/limited oracle exact. The comparison ignores only CPU time and peak RSS; all logical outcomes, costs, traces, certificates, oracle counts and semantic checks must agree. Wall time, CPU and RSS depend on the host and are not required to match bit-for-bit.

The first campaign records remain under `results/evaluation/`; `results/summary/` contains their derived tables. `results/reproduction.json` records the actual clean-extraction replay, with compact copies of its manifest, summary, controls, unit-test log and timing under `results/replay-*`. The duplicate replay case directory was removed only after exact logical comparison and is deterministically regenerated by the commands above. Replaying spends additional resources: the original campaign budget charged both the first campaign and its clean replay rather than treating repetitions as free.

The runner caps the evaluation at 600,000 enumeration units, 364 cases and 2,700 cumulative process CPU-seconds; individual exact searches have 50,000-discovered-state and 15-CPU-second caps. Its admission interval is bounded, but this script is not an operating-system job scheduler. A user rerun should retain an external 300-second per-invocation timeout where available. The original complete campaign had a stricter one-million-unit cumulative cap including pilots, construction, negative controls and clean replay.

## Retained inputs and evaluation interpretation

`instances/campaign/` contains the exact selected 364 JSON inputs; these are the reproduction inputs. They are original constructed mathematical instances, not a downloaded workload collection. There are 256 structural-grid cases, 16 larger structural checks, eight separation instances, 24 scaling instances, 54 exact-integer IR instances, four retained fixed controls, and two hardness controls. Selection and interpretation are detailed in `instances/README.md`. The observed maxima are 64 vertices and 117 recipes (the frozen recipe ceiling is 192); the precision alphabet is exactly 8/16/32/64 bits and capacity is at most 1,024 units.

The first campaign completed 286 configuration oracles, with 283 applicable oracle/recurrence agreements, and checked 361 Bellman certificates. It charged 166,841 enumeration units. All 54 integer-IR instances remain: 48 typed feasible, 36 fixed-64 feasible, 12 typed-only, and six infeasible in both. All 36 jointly feasible cases reduce I/O through precision selection; **none** shows an I/O gain from preparation over the contiguous typed policy. The seven-node expansive valley is a deliberately inapplicable case: exact optimum 33, preparation-policy bound 35, contiguous policy 49.

The summary's `preparation_improvements_by_group` field compares the preparation **policy** with the contiguous policy; the control-group count includes the expansive valley. It must not be described as two exactness demonstrations. Only the contractive 89/91 control and eight analytic-family instances isolate a proved preparation gain.

## Files and reproducibility boundaries

- `src/`: typed model and optimizer, configuration oracle, event and Bellman checkers, generators, exact-integer front end, and a literal fixed-weight reference-policy reimplementation.
- `proofs/core.md`: complete written proofs, finite-check boundaries and hardness construction.
- `instances/`, `results/`: exact inputs, pilot evidence, original campaign outputs, certificates, event witnesses, and summary data.
- `tools/`: deterministic input construction, fixed corruption controls, the literal reference-equation evaluator, bibliography consistency audit, summary generation and clean-replay comparison.
- `claim_evidence_ledger.csv`, `external_resources.csv`, `bibliography-verification.csv`: claim-level traceability, source/license attribution, and the role/identifier inventory for every manuscript reference.

The reference policy implements the published mathematical Eq. (6) from Bhattacharjee et al., SPAA 2025, DOI 10.1145/3694906.3743342; it is not their software and does not reproduce their devices or workloads. No external baseline internals were modified. Exact original inputs and all newly authored code are included. Python and the TeX toolchain are environmental dependencies, not vendored or fingerprinted. The logical standard-library replay was checked on one available environment; cross-interpreter and cross-platform equivalence is not experimentally certified.

### Parent-project bibliography audit

The standalone repository intentionally does not contain the manuscript. From `artifact/` inside the complete project tree, the following offline command checks that every bibliography entry is cited, every citation resolves to a BibTeX key, no DOI is duplicated, all required fields are present, the 1:1 source-verification ledger agrees on key/title/year/identifier/status, and the bibliography contains at least 31 entries:

```sh
python3 tools/audit_bibliography.py \
  --tex ../paper/main.tex \
  --bib ../paper/references.bib \
  --verification bibliography-verification.csv \
  --minimum 31 \
  --output results/bibliography-audit.json
```

This is a consistency and identifier audit, not a substitute for reading sources. `bibliography-verification.csv` records the source role and verification basis; the anchor paper's exact model, Eq. (6), Eq. (7), Lemma 3.7, and Theorem 3.8 were rechecked against the complete primary-source PDF.
